## 1. Мета й вимоги користувача
- **ЗАКОН УНІВЕРСАЛЬНОСТІ (рішення користувача 2026-11-13, для путівника й компаньйона):** приклад із гри — лише ілюстрація вади; правило робимо для всього, що має такі самі дані (форма запису, компоненти, тег, роль слота…), замір і тест — по всіх предметах / рецептах / квестах, а не на одному прикладі. Повний текст — `ATM11-Companion/HANDOFF.md` §5.
- **Вкладка «Клавіші»** (ідея користувача, зроблено в GK): графічна клавіатура й миша з поточними клавішами гри й модів (з `options.txt`), конфлікти, непризначені важливі дії, групування за категоріями або модами, моди — посиланнями; оновлюється при зміні клавіш у грі (`start.bat` → 2) або завантаженням свого options.txt у браузері. Клавіатура користувача — **Hator Skyfall TKL PRO (ANSI TKL 87, без цифрового блока)**. Специфікація й аналіз — `design/KEYBINDS.md`.
- Інтерактивний сайт-путівник по ATM11 (новий світ користувача): **дорожня карта** прогресу (етапи × групи модів, синергії), **довідник модів** з класами-бейджами, **гілки** (магія, техніка, виміри, боси) зі схемами, **квести** українською, позначки «зроблено».
- Мета гри: не прогавити цікаві механіки й не застрягнути в грінді — що з чим поєднувати в кожен момент.
- **Спойлери — так, але згорнуті** (боси, ендгейм, ATM Star — `spoiler: true` / компонент spoiler).
- Темний «ігровий» стиль. Модульна архітектура (за зразком pon-app користувача: ES-модулі без збирача, `// @ts-check`, `types.d.ts`, DOCUMENTATION/CHANGELOG, `.agent/workflows`). Файли — до ~300 рядків.
- Публікація: користувач викладе в GitHub і ввімкне **GitHub Pages з теки `docs/`**. Тому всі шляхи відносні, бібліотеки локальні (`docs/vendor`), регістр імен файлів — точний (Pages чутливий до регістру), `docs/.nojekyll` (G8). Рішення користувача (2026-11-06): `docs/data/names.json` (≈6 МБ, лише для моста) лишається в `docs/`; знімки прогресу `docs/data/progress*.json` (нікнейм, UUID, світи) — публікуються.
- Схеми: **ELK.js + власний SVG** — дорожня карта (дерево розвитку v2); **Cytoscape.js** — глави квестів; мапа синергій (G7) — ELK + HTML-картки + SVG (рішення користувача 2026-11-06: силовий граф Cytoscape на 112 модів нечитабельний); **jsPlumb** — малі схеми в гілках.

- **Жодної вигаданої механіки (вимога користувача 2026-10-27).** Дорожня карта, гілки, квести, класи, синергії й залежності мають бути «іграбельними» — такими, як їх реалізує бекенд збірки. Кожне твердження на сайті має джерело (квест FTB, рецепт у jar / KubeJS, конфіг, lang); залежність `req` на карті — лише якщо її дає залежність квестів або рецепт (джерело — у полі ребра `src`); синергія — лише якщо є рецепт / механіка, що поєднує моди. **Що таке синергія (уточнення користувача 2026-10-27):** не лише залежність крафту, а все, що краще використовувати разом — напр. для енергії: що виробляє, що проводить, що зберігає, де заряджається, що передає дистанційно чи живить; так само для предметів, рідин, мобів тощо. Але механіка має бути реальною в збірці (обидва моди справді підтримують FE / предмети / рідини, є сумісність) і вказана в `src`. Моди, яких у збірці немає, не згадувати як доступні (лише з поясненням «у збірці немає»). Що не підтвердилось — прибрати або ⚑. Перевірка: `tools/audit_fidelity.py` → `raw/audit_fidelity.md` (має прямувати до нуля у розділах «виправити»).
- **Сито (рішення користувача 2026-10-27, сесія S):** усе, що йде на сайт і в компаньйон, проходить машинну перевірку проти ПОВНИХ індексів бекенду (`raw/*_index.json`), а не пильність моделі: поруч із людським `src` — машинне `ref` (§3), audit_fidelity розв'язує його; не знайдено / неактивне — «виправити». Висновки — з повного розбору файлів (індекси, `tools/idxq.py`), не з grep-фрагментів. Нові синергії — лише з `raw/crossmod.md` або механік, підтверджених ref.
- **Сито — не замінник критичного мислення (рішення користувача 2026-10-28).** `ref` доводить, що джерело існує, а не що воно доводить саме цю фразу (G6: «сплав лише у сфері Powah» мав справжній рецепт Powah, але «лише» було неправдою; квест з помилкою перекладу пройшов як джерело). Тому кожне твердження читати як гіпотезу: який механізм гри за ним стоїть → де він у файлах збірки → чи доводить джерело саме це (числа, «лише / єдиний / завжди / усі», вимір / біом / структура) → чи не суперечить англійському оригіналу квесту й іншим записам путівника. Мета — логіка й зв'язки збірки «як на долоні»: кожен міжмодовий механізм описано один раз (`content/facts.json` або опис мода-власника), решта посилається на нього, а не переказує.
- **Користувач ATM11 ще не грав** (колись грав ATM 6/7) і покладається на реверс-інжиніринг збірки: факти брати з файлів збірки, а не «з пам'яті». Порядок джерел: KubeJS (`minecraft/kubejs/server_scripts` — змінені/вимкнені рецепти, умови `Platform.isLoaded`) → конфіги (`minecraft/config/*.toml` — радіуси, місткості, вимкнені функції) → типові клавіші (`minecraft/options.txt`) → jar (`tools/jarq.py`: lang-підказки, рецепти, предмети) → квести й книги → desc_en. `verify: true` («⚑ Чернетка») — лише те, що не вдалося підтвердити даними; етапи (`stage`) — за вартістю рецептів (`jarq.py uses`).

## 2а. Архітектура даних (рішення користувача 2026-10-27 — НЕ переробляти)
Шаблон — «статична база, зібрана скриптом» (static site generator): одна база знань у файлах, пише її лише один процес, сайт і міст тільки читають. Реляційна БД / сервер не потрібні: один автор, рідкі оновлення, лише читання, GitHub Pages не запускає сервер.

| Як у БД | У нас |
|---|---|
| Таблиці | `docs/data/*.json` (моди, віхи, квести, предмети, клавіші, факти…) |
| Первинний ключ | ID: мод `ae2`, віха `tr_atm`, квест (hex), предмет `ns:id` |
| Зовнішній ключ / цілісність | `build_data.py` (посилання, «попереджень 0») + `audit_fidelity.py` (джерела, «виправити 0») |
| INSERT / UPDATE | правка `content/` або нові файли гри → `build_data.py` (**єдиний, хто пише базу**) |
| SELECT | сайт і міст ATM11-Companion читають `docs/data` |
| ETL | екстрактори `tools/extract_*.py`: jar, квести FTB, KubeJS, конфіги, переклад → `raw/` → база |

- **Знання** (моди, квести, карта, назви українською) — лише з файлів збірки й `content/` → `build_data` → `docs/data`. Ні сайт, ні міст не читають jar / `effective.tsv` / квести напряму й не рахують те саме своїм кодом.
- **Живий стан гри** (сейв, лог, згодом клієнтський KubeJS) — лише міст (`game-watcher`). Сайт бере його: міст → тека гри, вказана в браузері → знімок `progress.json`; завжди показує джерело й час. Ручні позначки «Зроблено» — лише браузер.
- **Одне оновлення:** оновилась збірка / переклад → екстрактори + `build_data` на ПК (лише там є гра) → міст бачить одразу; онлайн-сайт (GitHub Pages) — дзеркало `docs/` після `git push` користувача.
- Новий факт → у `content/` або екстрактор, не в міст; новий живий сигнал гри → у міст, сайт отримує його через міст.
- Рецепти — пізніше (рішення користувача): спершу довести до ідеалу всі дані гри та їхні взаємозв'язки. Коли дійде — `build_data` збере ще й SQLite-файл у `docs/data` (теж лише читання).
- **Зроблено в C2:** міст компаньйона читає базу одним модулем (`services/guide-data.js`), назви — `docs/data/names.json` (build_names.py), без власного читання `effective.tsv` / ATM11-UA і вписаних у код словників; стани віх (`tree-state.js`) і клавіші (`keys-model.js`) — імпорт модулів сайту; відбиток бази `meta.json → fingerprint` → `/state → base`, `#/assistant` попереджає «міст на старій базі»; `start.bat` → 4 «Оновити все»; міст роздає сайт на `http://127.0.0.1:8812/site/`. Подробиці — `ATM11-Companion/HANDOFF.md`.

## 3. Схема ручного вмісту (content/)
**content/mods/<група>.json** — `{ "<modid>": {…}, … }` (ключі `_…` — коментарі):
- `cls`: ["magic", "exploration"] — класи з classes.json, перший — головний; **давати ВСІ категорії, до яких мод належить** (рішення користувача), а не одну-дві
- `role`: content | addon | qol | library | perf;  `parent`: "ae2" (для доповнень)
- `uk`: 1–2 речення — що це і навіщо гравцю (головне поле!)
- `what`: ["додає …", …] — ключові можливості (3–6 пунктів);  `stage`: ["s2", "s3"] — коли актуальний
- `synergy`: [{"mod": "ae2", "why": "…", "src": "…"}] — з чим поєднувати (визначення — §1); **`src` обов'язкове** — рецепт / тег / конфіг / сумісність мода (сторінка мода показує «Джерело»); `audit_fidelity.py` вимагає його для класів у `SYN_AUDITED` (з G6c — усі класи); синергія — лише з рецептом / тегом / конфігом / класом сумісності, що стосується партнера; пару описують **один раз** (мод-власник механізму) — сторінка партнера сама показує її як `synergy_in` (G6b); «спільна глава», «альтернатива», «аддон розширює батька» — не синергія; пара в обидва боки (A → B і B → A) — лише для різних механізмів і з `pair_ok: "чому"` в одному із записів (G7: аудит ловить і дублікати з різними ref);  `tips`: ["…"];  `spoiler`: "…" (згорнуто)
- `chapter`: файл глави квестів;  `book`: назва книги в грі;  `branch`: id гілки
- `ref`: машинні джерела тексту мода (`uk` / `what` / `tips` / `spoiler`): ID — `item:` / `recipe:`, числа з конфігів — `config:…=<значення>` (сито звіряє число з текстом); обов'язковий для головного cls у `TXT_AUDITED` (audit_fidelity.py; з G6c — усі класи). Пункт `what` / `tips` — рядок або `{"t": текст, "ref": …}` (власні ref пункту; build_data → рядки + `item_ref`). `abs_ok: "причина"` — свідомий виняток для «лише / усі» (G6b)
Мод без запису показується з автокласом (пунктирний бейдж) — `build_data.py` визначає library/perf/qol евристикою.
- `verify`: true — «⚑ Чернетка» (не підтверджено даними збірки) на сторінці мода;  `parent` — сторінка батька сама показує список доповнень
- `icons`: ["ae2:controller", …] — ключові предмети мода (іконки);  `features`: ["boss", …] — ПОВНІСТЮ замінює автовизначені піктограми; **автовизначення неточне — для кожного описаного мода перевіряти й записувати `features` явно** (виміри — dimension/*.json; боси — тег c:bosses, виняток — дракони Ice and Fire (рішення користувача 2026-10-28); данжі — будь-яка структура; біоми; руди — placed_feature з ore; істоти — ≥2 яєць виклику) (dimension | boss | dungeon | biome | ores | mobs);  `dims`: [{id, name}] — замінює автоназви вимірів
**roadmap.json** (дерево v2, design/ROADMAP_V2.md) — `groups`: [{id, title, cls, mods[], desc?}] (сузір'я); вузол: `id, stage, lane, group, trunk?, star?, title, icons[], mods[], features?, chapter?, spoiler?, verify?, na?, text, done_by: {quests?: [hexId], advancements?: [id], items?: [id]}`; ребро: `from, to, kind` (req | syn | opt), `label?`, `src?`.
  - **`src` обов'язкове для req і syn** (build_data попереджає): звідки зв'язок — «квести «Розділ 1»: «X» ← «Y»», «рецепт ns:id — …», «KubeJS mods/…/recipes.js: …», «config/…: …», біом / `biome_modifier`. Сайт показує його в панелі віхи й у підказці над лінією. Синергія — лише з рецептом / механікою, що поєднує моди. `opt` — «варіант» без твердження про залежність.
  - `na: "причина"` — віха «у цій версії збірки недоступно» (ATM Star): стан ∅, без done_by і без «Зроблено».
  - `trunk: true` — стовбур: ланцюжок квестів «Розділу 1/2» Вдарте дерево → … → Незер → Незерит → Усемодій → Виміри ATM → Вібраній і унобтаній (один ланцюжок — інакше вертикаль ламається; Енд — гілка від Незеру). `star` — значок ★ «потрібно для ATM Star»; зараз не використовується (зірку не зібрати).
  - `lane` — колір і бік дерева (ліворуч: storage, logistics, farming, resources, gear, exploration — `LEFT_LANES` в elk-layout.js; решта праворуч).
  - Стан «доступно» рахується з ребер `req` (усі виконано), без них — хоч один попередник. Ребра лише згори вниз (етап from ≤ to — build_data перевіряє).
  - Позиції рахує ELK у браузері; налагодження: `#/roadmap?elk.<параметр>=<значення>` (напр. `elk.spacing.nodeNode=50`).
**Іконки** — будь-яке поле `icons` / `icon` з ID предметів; після додавання: `tools/extract_icons.py` → `tools/build_data.py` (попередить, якщо іконки немає). Шукати ID: `extract_icons.py --find "occultism:.*chalk"`.
**branches/<id>.json** — `title, icon, cls, mods[], chapter, book, enter (етап), summary, gives[], steps[{id, x, y, title, text, src, quests?[hex], spoiler?}], links[[from, to]], _src`. x, y — клітинки сітки 230×110. Крок = квести глави FTB (`quests` → build_data додає `q` з назвами; крок «виконано» автоматично, коли в сейві виконано всі його квести) + `src` (обов'язково: квест / книга / рецепт / KubeJS / конфіг). Гілка — лише для мода з відкритою главою квестів; частини глави, що в збірці не працюють (моди-заглушки), — не кроками, а реченням у `summary`. Посилання «🌿 Гілка» на сторінці мода й у панелі віхи — автоматично за спільними `mods`.
**chapters/<глава>.json** (вкладка «Квести»; ім'я файлу = `file` глави з chapters.json) — `ov` (огляд, 2–4 речення: що дає глава гравцю), `steps[]` (порядок проходження), `rewards[]` (ключові нагороди), `atm[]` (особливості ATM11 — лише з KubeJS / конфігів / рецептів), `why` (**лише й обов'язково** для прихованої глави), `verify`, `notes: {<id квесту>: "текст" | {text, title?, verify?}}` (дописи до квестів без опису; `title` — якщо назви немає й у книзі), `_src` — звідки факти; **сито (G6d):** `ref` — джерела ov / why, пункт steps / rewards / atm — рядок або `{"t", "ref", "abs_ok"?}`, допис — `{"text", "ref", "title"?}` — ref обов'язковий для всього (аудит «глава без ref»); why прихованої глави — `file:config/ftbquests/quests/chapters/<глава>.json5~always_invisible: true` + `count:stubs:` / `count:qall:` / `count:items:<мод>=0`; механізм, однаковий для багатьох квестів, — один раз в `atm`, допис посилається («Як зробити форму — у «Особливостях ATM11» глави»). build_data попереджає: невідома глава/квест, допис до службового квесту, прихована глава без `why`. Огляди й дописи не дублюють опис квесту з книги; шаблонні дописи (100 однакових «насіння X») не писати — загальне правило глави йде в `atm`.
**keys.json** (вкладка «Клавіші», design/KEYBINDS.md) — `cats`, `ctxs`, `rules`: правила згори вниз **каскадом** (пізніше уточнює раннє), збіг — `re` (regex за id дії) і/або `ns` (повний збіг простору імен). Поля: `cat`, `ctx` (game | held | vehicle | gui | debug), `scr` (для gui: `c:*` — будь-яке вікно з інвентарем, `c:<ім'я>`, `quests`, `map`, `jei-recipes`…), `nc` (не конфліктує: модифікатор/дія над елементом), `soft` (умовна — конфлікт лише «можливий»), `important`, `note`, `mod`/`name` (власник і назва, якщо їх немає в перекладі); `null` — скинути поле. `plan`: [{id, to («Ctrl+G» | «F8» | «none»), why}] — план перепризначень (build перевіряє, що не створює конфлікту; `raw/keys_plan.txt` — рядки для options.txt). Схема `docs/data/keys.json` і правила конфлікту — DOCUMENTATION.md. Пари дій одного мода не конфліктують; «з предметом» × «у світі» — лише можливий конфлікт (рішення користувача).
**ref — машинне джерело (сито, S; таблиця схем — DOCUMENTATION «Сито достовірності»)** — рядок або список поруч із `src` у `synergy[]`, ребрах карти, кроках гілок (їхні `quests` — теж ref), фактах (віхах — за бажанням): `quest:<hex>` · `recipe:<id>` (jar / дані / KubeJS) · `kjs:<файл від kubejs/>[#<id рецепта> | #L<рядок>]` · `tag:<ns:path>` · `config:<файл>#<ключ>[=<значення>]` · `item:<ns:id>` · `lang:<ключ>` · `jarfile:[<jar>!]<шлях>[~<текст у файлі>]` · `file:<шлях від minecraft/>[~<текст>]`; `!<ref>` — «вимкнено / немає / приховано» (проходить, лише якщо ref НЕ розв'язується); G6b: `quest:<hex>~<цитата>` (квест містить текст), `count:<що>:<вибірка>=<N>` (сито перераховує кількість: files / items / recipes / quests / tag / config / json / dir / rx), `only:<предмет>=<тип|мод>` («лише / єдиний спосіб»). **Перевірки G6b** (DOCUMENTATION «Сито»): кожне число тексту — серед доказів ref; речення з «лише / усі / завжди…» — не більше, ніж доказів повноти (`!`, `only:`, цитата) або `abs_ok`; англійський оригінал квесту поруч; дублікати пари A ⇄ B. Обов'язкові (audit «виправити»): кроки гілок, synergy і тексти модів усіх класів (`SYN_AUDITED` / `TXT_AUDITED`, G6c), ребра req/syn віх цих класів без підтвердження квестами, усі факти. config-ref стосується мода зі шляху файлу (config/ironjetpacks/… → ironjetpacks), quest-ref — модів завдань, нагород і варіантів смарт-фільтра. Синергія проходить, лише якщо ref стосується мода-партнера; число з config-ref мусить бути в тексті. `ingame: "що перевірити"` — рішення користувача перевірити в грі: аудит → «інфо», сайт — «⚑ Перевірити в грі». Шукати ref: `tools/idxq.py` (`check`, `uses`, `pair`, `kjs`, `cfg`), кандидати синергій — `raw/crossmod.md`.
Перевірка: `build_data.py` попереджає про невідомі моди, класи, етапи, вузли, дії без категорії/контексту, правила без збігів, зайняті поради, ref невідомого формату (усе має бути 0).
